### CRITICAL BLOCKER: `Ccs::satisfied_by` OOM
- **File**: `poker_zkvm/src/ccs/mod.rs` lines 298-338
- **Problem**: The method materializes `mz: Vec<Vec<Fr>>` — a dense `matrices.len() × num_rows` matrix. For SHA-256 full mode: ~600K matrices × ~170K rows = ~102 billion Fr elements ≈ **3.26 TB** of memory. This will OOM/hang.
- **Root cause**: `SparseMatrix::evaluate(z)` returns `vec![Fr::zero(); num_rows]` — a dense vector — even when the matrix has only 1 non-zero entry (row-isolated, as generated by `CcsBuilder`).
- **Impact**: ALL full-mode tests that call `satisfied_by` will fail.

## Proposed Changes

### Step 1: Optimize `Ccs::satisfied_by` for row-isolated matrices

**File**: `poker_zkvm/src/precompiles/../ccs/mod.rs` (i.e., `poker_zkvm/src/ccs/mod.rs`)

**What**: Add a fast path to `satisfied_by` that detects row-isolated matrices (≤1 entry per matrix, as generated by `CcsBuilder`) and computes the constraint sum in O(matrices + subsets + num_rows) time/memory instead of O(matrices × num_rows).

**Why**: Without this optimization, the SHA-256 full circuit (and any future large circuit built with `CcsBuilder`) cannot be verified. The current dense approach is infeasible for circuits with >100K rows.

**How**: Replace the body of `satisfied_by` with a dual-path strategy:

```rust
pub fn satisfied_by(&self, z: &[Fr]) -> Result<bool, ZkvmError> {
    if z.len() != self.num_vars {
        return Err(ZkvmError::Other(format!(
            "Ccs::satisfied_by: z.len() {} != num_vars {}",
            z.len(),
            self.num_vars
        )));
    }

    let num_rows = self.num_rows();
    if num_rows == 0 || self.matrices.is_empty() {
        return Ok(true);
    }

    // Fast path: all matrices are row-isolated (≤1 entry each)
    // CcsBuilder-generated CCS always satisfies this condition
    let all_row_isolated = self.matrices.iter().all(|m| m.entries.len() <= 1);

    if all_row_isolated {
        return self.satisfied_by_row_isolated(z, num_rows);
    }

    // Slow path: general case (matrices with multiple entries)
    self.satisfied_by_general(z, num_rows)
}
```

Add two private helper methods:

1. **`satisfied_by_row_isolated`** — O(matrices + subsets + num_rows):
   - For each matrix j with 1 entry: precompute `(row_j, M_j·z at row_j)` = `(entry.row, entry.value * z[entry.col])`
   - For empty matrices: `(0, Fr::zero())`
   - Group subsets by row: for each subset S_i, all matrices should have the same row (CcsBuilder guarantees this); compute `c_i * Π_j (M_j·z)` at that row
   - Accumulate into `row_sums: Vec<Fr>` of length `num_rows`
   - Check all `row_sums` are zero

2. **`satisfied_by_general`** — original O(matrices × num_rows) implementation, for backward compatibility with non-CcsBuilder CCS (e.g., hand-crafted matrices in tests).

**Safety**: The fast path correctly handles:
- Row-isolated matrices with 1 entry (CcsBuilder output)
- Empty matrices (0 entries) — contribute 0 to all rows
- Subsets where matrices span different rows — product is 0, no contribution (correct CCS semantics)

**Test impact**: All existing `satisfied_by` tests continue to pass because:
- Small circuits use the fast path (all CcsBuilder-generated matrices have 1 entry)
- The MVP sha256/poseidon/ecdsa circuits use hand-crafted matrices (some may have multiple entries per matrix) → slow path
- Both paths produce identical results

## Assumptions & Decisions

1. **`satisfied_by` optimization is safe and backward-compatible**: The fast path produces identical results to the slow path for row-isolated matrices. Non-row-isolated matrices (hand-crafted in some tests) fall back to the slow path. All existing tests pass with both paths.

2. **The SHA-256 full circuit code is correct**: Based on code review, the `FullBuilder` methods correctly mirror `bit_ops` constraint structures while computing witness values simultaneously. The CCS structure is input-independent, so `build_ccs()` with dummy inputs produces the correct structure.

3. **Performance estimates**: With the optimization, each `run_full` call takes <1s, and each `satisfied_by` call takes <1s. Total test time <30s. Without the optimization, tests would OOM/hang indefinitely.

4. **No changes to B1 or B3**: Both are already complete and verified.

5. **The `satisfied_by` optimization benefits all future large circuits**: This is infrastructure work that enables not just SHA-256 full mode but also any future circuit built with `CcsBuilder` that has >10K rows.
