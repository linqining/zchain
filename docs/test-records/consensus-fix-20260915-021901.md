# zchain 4 节点共识出块问题 — 修复与验收记录（20260915-021901）

## 症状（本地复现 = 服务器同源）
- 链提交到 height 256 后永久卡死；node0/2/3 各 ~615 次
  `put_block 失败：block height 256 is already committed to a different hash`；
  FORK ANCHOR WARNING 刷屏；P2P 连接抖动放大故障。

## 根因 1（主卡点）：height_index key 用 little-endian 编码
- `get_tip_height` = height_cf RocksDB End 迭代（**字节序**最大）；
  LE 编码下 256(00 01..) 字节序 **小于** 255(FF 00..) → 高度 ≥256 后
  tip 恒返回 255 → 每轮装配 height=256 → put_block 冲突 → 永动卡死。
- `get_range`（RequestBlocksByRange 的实现）同样按字节序 From/比较 →
  跨 256 的范围查询乱序/丢块 → catch-up 失效。

### 修复
- `block_store.rs`：height_index key 全部迁移 **big-endian**
  （put/get_by_height/get_tip_height/get_tip_hash/get_range/prune_old_blocks，
  共 8 处）。BE 下数值序=字节序，全部迭代/比较自然正确。
- 注意：key 编码变化 → 旧 RocksDB 不兼容，部署必须清数据
  （deploy_4node.sh 已有清数据逻辑；服务器同）。

## 根因 2（分叉防线）：CommitVote 去重按 commit_round 而非 height
- 视图切换令 commit_round 前进而 height 不动 → 同一 signer 对同一 height
  的不同 cert 票共存 → 两个 cert 各自凑 3/4 quorum → 同高双块分叉
  （实测 node0 提交 256/A、node1 链停在 55）。

### 修复
- `CommitVote` 增加 `height` 字段；VoteCollector 去重/替换键改为
  `(epoch, height, signer_pubkey)` last-write-wins → 任何时刻每
  (height, signer) 至多一票，双 quorum 数学不可能（3+3 > 4）。

## 根因 3（卡死后无恢复）
- put_block 冲突后装配循环每轮重试同 height，无权威块拉取。

### 修复
- 新增 `request_authoritative_block`：冲突时广播
  `RequestBlocksByRange(h, h)` 拉权威块，2s 退避限频
  （`BLOCK_CONFLICT_REQUEST_BACKOFF`）。

## 验收（本地 4 节点，200ms 块间隔）
- 全新部署 → 4 节点 tip 一致连续推进：121→139→156→174→192→**346**
  （**跨过 256 断裂点**）；
- `already committed` 冲突：0 次（修复前 345×3 节点）；
- FORK ANCHOR WARNING：0 次（修复前刷屏）；
- commit certificate 多签 4/4 票；
- `cargo test -p zchain` 17/17、`-p poker_l1 --lib` 1901/1901。

## 新发现（下一卡点，待处理）
- height 346 后全网 vertex 停产：epoch 33→34 切换（DAG 清空、round 重置 1）
  后产到 round=16 即停止（进程存活、无 ERROR、CPU 0%）——epoch 边界后
  validator 产块循环停滞。待定位：epoch 推进后的 parent 选择/leader 成熟度
  门（L2 mature_cap / authors_settled）在新 epoch DAG 上的阻塞点。
- `request_blocks_by_range` 的响应读取与 CommitVote gossip 共用连接流，
  读到非预期消息仅告警（应 continue 跳过继续等 ResponseBlocks）。

## 追加（同日晚间续跑）：346 停滞 = epoch 边界三重叠加 + 协议级遗留

### 已修复并验证
1. **广播写死锁**（本轮新根因）：`gossip_broadcast` 的 per-stream
   `write_all` 无写超时——半开死连接阻塞至 TCP 重传超时（15min+），
   持 per-stream 写锁令所有广播排队、validator loop 停产。修复：
   trait `P2pIo::set_broadcast_write_timeout`（TcpStream 2s 超时），
   超时快速失败并移除死连接。验证：三节点跨 346 持续出块。
2. **vote.height catch-up**：收票处检测 vote.height 超过本地 tip →
   广播 RequestBlocksByRange(tip+1, vote.height)；
   `request_blocks_by_range` 重写为带谓词读循环（跳过 gossip 混流，
   只接受首块==start 的区间）。
3. **epoch 跟随多数派**：vertex 准入遇 InvalidVertexEpoch(actual>expected)
   时连续 advance_epoch_with_vrf 到 actual 并重试准入；validator loop
   检测 node epoch 变化自动清 DAG/重置 round。

### 遗留（协议级，需专项）
**多装配者块字节不唯一**：每个 validator 用自己收到的投票子集装配块
（签名列表不同 → 块字节/hash 不同），"语句级去重"允许同语义变体共存。
后果：各节点的 prev_hash 链指向各自变体——同语义不同哈希的平行链，
跨节点块互不承认（invalid prev_hash / not strictly increasing），
掉队节点无法用运行时 catch-up 恢复（需状态回退或重置）。
实测：全新 4 节点在 epoch 边界（cert_round 170/171/172）tip 分裂后
commit 停滞（vertex round 继续涨、块高不动）。

**修复方向（二选一，需专项评审）**：
- A. leader-only 装配：仅 leader 装配完整块并广播，其余 validator 只
  验证并接受（块字节全网唯一，改动点集中在 commit 流程）；
- B. prev_hash 语义改为「父块语句哈希」（cert signing_hash），块字节
  不再进入哈希链（影响 light client 与存储寻址，改动面大）。

验证快照（2026-09-15 04:15）：全新 4 节点推进至 52/51/30/51 后在
epoch 边界停滞；零 already-committed 冲突、零 FORK ANCHOR 误报；
`zchain` 17/17、`poker_l1 --lib` 1901/1901。

## 方案 A 验收追加（2026-09-15 09:17）

### 已实施
- **leader-only 装配门** + **leader 超时兜底**（leader 超过
  COMMIT_VOTE_PIN_RELEASE(5s) 未出块时，距投票最久的 follower 兜底装配；
  兜底块与 leader 块同语句，put_block 语句级去重保证无分叉）。
- **catch-up epoch 跟随**：区间导入的每块成功后按
  `ceil(tip_cert_round / EPOCH_LENGTH)` 推进 node epoch（修复空库节点
  catch-up 卡 epoch 0/1）。
- **重启 round 恢复**：`get_by_author(author).max(round)+1`（修复数据
  保留重启的 equivocation）。
- **自连过滤**：`connect_peer` 拒绝自身 listen 地址（PEX 会把自身地址
  广播回来，自连接 churn 曾达 1700+ 次并污染 catch-up 轮询）。
- 广播写超时 2s→10s（同机 debug 构建写延迟峰值下 2s 误杀活连接）。
